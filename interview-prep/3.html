1 · Core Concept

What is REST?

REST stands for Representational State Transfer. It is an architectural style for designing networked applications, especially web APIs. REST was introduced by Roy Fielding in his doctoral dissertation.

Interview definition:
REST is an architectural style for building scalable web services around resources, where clients interact with those resources using standard HTTP operations such as GET, POST, PUT, PATCH, and DELETE.

A REST API normally exposes resources through URLs and uses HTTP semantics to perform operations on those resources. The server returns a representation of the resource, commonly JSON.

Simple example

GET https://api.example.com/api/products/101

Here, /products/101 identifies the product resource with ID 101. The server may return a JSON representation such as: 

{
  "id": 101,
  "name": "Laptop",
  "price": 65000,
  "category": "Electronics"
}
2 · Architecture

Six REST Architectural Constraints

1. Client–Server

Client and server have separate responsibilities. The client handles the UI and user interaction; the server manages data and business logic.

2. Stateless

Each request contains all information necessary for the server to process it. The server does not depend on stored client-session state between requests.

3. Cacheable

Responses should explicitly indicate whether they can be cached. HTTP caching can improve performance and reduce server load.

4. Uniform Interface

Resources are accessed consistently using standardized resource identification, representations, HTTP methods, and self-descriptive messages.

5. Layered System

A client does not necessarily know whether it is communicating directly with the origin server or through proxies, gateways, load balancers, or other layers.

6. Code-on-Demand (Optional)

A server may optionally send executable code to extend client functionality. This is the only optional REST constraint.

3 · Resource-Oriented Design

What is a Resource in REST?

A resource is any meaningful entity that the API exposes to clients: a user, product, order, customer, invoice, vehicle, or collection of records.

Good resource URLs

GET /api/products
GET /api/products/101
GET /api/customers/25/orders
GET /api/orders/5001

Avoid action-oriented URLs

GET /api/getProducts
POST /api/createProduct
POST /api/deleteProduct
POST /api/updateProduct

REST prefers nouns representing resources. The HTTP method communicates the intended operation.

6 · ASP.NET Core

REST API Example in ASP.NET Core

Below is a simple controller demonstrating resource-oriented REST endpoints.

Model

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
}

Controller

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private static readonly List<Product> Products = new()
    {
        new Product { Id = 1, Name = "Laptop", Price = 65000 },
        new Product { Id = 2, Name = "Monitor", Price = 18000 }
    };

    [HttpGet]
    public ActionResult<IEnumerable<Product>> GetAll()
    {
        return Ok(Products);
    }

    [HttpGet("{id}")]
    public ActionResult<Product> GetById(int id)
    {
        var product = Products.FirstOrDefault(x => x.Id == id);

        if (product == null)
            return NotFound();

        return Ok(product);
    }

    [HttpPost]
    public ActionResult<Product> Create(Product product)
    {
        product.Id = Products.Max(x => x.Id) + 1;
        Products.Add(product);

        return CreatedAtAction(
            nameof(GetById),
            new { id = product.Id },
            product);
    }

    [HttpDelete("{id}")]
    public IActionResult Delete(int id)
    {
        var product = Products.FirstOrDefault(x => x.Id == id);

        if (product == null)
            return NotFound();

        Products.Remove(product);
        return NoContent();
    }
}

Resulting endpoints

GET     /api/products
GET     /api/products/1
POST    /api/products
DELETE  /api/products/1
7 · API Design

REST URI Design Best Practices

  1. Use nouns rather than verbs: /products, not /getProducts.
  2. Use plural resource names consistently: /customers, /orders.
  3. Use path parameters to identify a resource: /products/101.
  4. Use query parameters for filtering, sorting, pagination, and search.
  5. Use HTTP status codes instead of returning HTTP 200 for every situation.
  6. Keep URLs readable and predictable.
  7. Use API versioning when backward-compatible evolution requires it.

Filtering and pagination

GET /api/products?category=laptop&page=2&pageSize=20
GET /api/products?sort=price&order=desc
8 · Key Interview Concept

What Does Stateless Mean?

In a RESTful system, every request should contain the information necessary for the server to understand and process it. The server should not rely on conversational session state stored from an earlier request. 

GET /api/orders/5001
Authorization: Bearer eyJ...

GET /api/orders/5002
Authorization: Bearer eyJ...

Each request independently carries its authentication context. This makes horizontal scaling easier because a request can be routed to any healthy server instance.

Important: Stateless does not mean the application has no state. Business data can absolutely be stored in databases, caches, or other systems. It means the server does not depend on client-session state from previous requests to understand the current request.

10 · Interview Ready

How to Answer in an Interview

Short answer: REST stands for Representational State Transfer. It is an architectural style for designing web services around resources. REST APIs typically use HTTP methods such as GET, POST, PUT, PATCH, and DELETE to manipulate resources identified by URLs. A RESTful API follows constraints such as client-server separation, statelessness, cacheability, a uniform interface, and a layered system.

Example: In a product API, GET /api/products/101 retrieves product 101, POST /api/products creates a product, PUT /api/products/101 replaces it, and DELETE /api/products/101 removes it. The API uses appropriate HTTP status codes such as 200, 201, 204, 400, 401, 403, and 404.
